## 3. Working method

1. **Start:** read `analyze-combined.md` §§ Verdict, Headline findings, 15 (plan) and 16 (user reports) yourself; read other sections only when briefing a worker. Create `fix-progress.md` (untracked, add to `.git/info/exclude`) with a status table `ID | workstream | status (todo / in progress / fixed <commit> / deferred <reason>) | verification`. Update it after every merge. On any resume, read it and `git status` first.
2. **Branching:** `git checkout -b fix/audit main`. Each worker branches from the current `fix/audit` tip in its worktree (`fix/audit-<ws>`). You merge, resolve conflicts (only in the hotspot files listed in §4), build, run tests, commit on `fix/audit` with a message that names the IDs (`fix(playback): PLAY-01 PLAY-02 PLAY-06 — …`). Do not push unless asked.
3. **Every worker brief** (workers do not see this file or the audit unless you point them to it) must contain: the goal; the finding IDs with the **exact section text** or a pointer "read `analyze-combined.md` lines A–B"; the list of files it owns and the files it must not touch; the build/test command and the rule "build must pass before you report"; "no lint suppression, no loosening of tests, no secrets in code, no unrelated refactors"; and the report format: changed files, IDs addressed, tests added and their results (verbatim summary lines), residual risks, **requested edits to hotspot files it was not allowed to touch** (exact diff), branch name.
4. **Verification ladder** (apply the highest rung that is feasible): JVM unit test (pure functions, parsers with fixtures, URL builders, validators) → instrumentation test on `emulator-5554` (Room migrations, cache export, service behaviour) → emulator smoke run → Codex review → static reasoning recorded in the progress note. Record which rung each ID reached.
5. **Lint:** the gate is "error count goes down and no new error class appears". Fix `UnsafeOptInUsageError` with `@OptIn(markerClass = UnstableApi.class)` at API boundaries (t2). Never add blanket `lintOptions { abortOnError false }` or `tools:ignore` to make it green.
6. **Scope discipline:** fix causes, not symptoms; no wholesale rewrite; no new dependencies unless a finding's fix needs one (say which); keep Russian UI strings as they are unless the finding is about them; do not implement the product features in §15 "Missing or partial capabilities" of the audit.
7. **Stop conditions:** if a workstream's second attempt still fails its verification, consult Codex once, then mark the ID `deferred` with the reason and move on — a deferred ID with an honest reason is better than a half-fix. If a hotspot merge conflict cannot be resolved cleanly, rebase the smaller branch rather than hand-merging code you have not read.
